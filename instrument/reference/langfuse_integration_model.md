Here's the complete picture, based on going through all 42 framework integration pages on langfuse.com/integrations (frameworks section only — model providers, gateways, no-code, analytics, dev tools, and "other" excluded as requested).

## Classification key

- **OTel (native)** — the framework has its own built-in OpenTelemetry support; you just point its OTLP exporter at Langfuse's `/api/public/otel` endpoint. No third-party instrumentation library needed.
- **OTel (3rd-party instrumentor)** — needs an external instrumentation library (mostly **OpenInference** from Arize, or **OpenLit**) that patches the framework and emits OTel spans, which Langfuse then ingests.
- **Custom package** — a dedicated exporter/module built specifically for Langfuse (or built into the framework specifically for Langfuse) that is *not* generic OTel and *not* the core `langfuse` SDK — e.g. `@mastra/langfuse`, `@voltagent/langfuse-exporter`, Swiftide's `langfuse` Cargo feature, AI SDK C++'s `ai::langfuse`.
- **Native Langfuse SDK** — done entirely with the plain `langfuse` (Python) or `@langfuse/`* package's built-in primitives (`CallbackHandler`, `@observe()`, `langfuse.openai` wrapper) — no OTel plumbing, no third-party instrumentor, no other extra package.

## Key takeaways

1. **Langfuse's own SDK is genuinely "native" only for the LangChain family (Python), Instructor, and Ragas.** Everywhere else — even for very popular frameworks like LlamaIndex, CrewAI, Google ADK, Agno, AutoGen, Semantic Kernel, SmolAgents — Langfuse relies on **OpenInference** (Arize's instrumentation library) or **OpenLit** doing the actual patching; Langfuse just receives the resulting OTel spans on its OTLP endpoint.
2. **Langfuse itself is built on OpenTelemetry under the hood** (v3+ Python/JS SDKs), so even the "native SDK" integrations are technically OTel internally — but the user doesn't have to touch OTel configuration directly.
3. **In JS/TS, almost nothing is "core SDK only" anymore** — since the v4 restructuring, JS integrations pull in separate `@langfuse/otel`, `@langfuse/langchain`, `@langfuse/tracing`, etc., packages rather than one monolithic `langfuse` package.
4. **Frameworks with their own built-in OTel** (Pydantic AI, LiveKit, Strands, Microsoft Agent Framework, Koog, Pipecat, Spring/Quarkus, Watsonx Orchestrate, LiteLLM) don't need any Arize/OpenLit instrumentor at all — you just redirect their existing OTLP exporter to Langfuse's endpoint with basic-auth headers.
5. **True Langfuse-authored "custom packages"** are rare and generally exist for frameworks maintained by *other* companies that built a first-party exporter (Mastra, VoltAgent) or where Langfuse ships language-specific glue code outside Python/JS (AI SDK C++, Swiftide/Rust).
